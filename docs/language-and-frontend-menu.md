# One language per program, and the Frontends menu in the shell (design; step 1 built)

Status: draft for the strategy; step 1 (language base, section 2.1) is built in this branch, steps 2 to 7 are design only. Covers finding B-L (mixed German/English in Store, Wiki, menus) and B-M (a "Frontends" menu in every window). Bases: ADR 0065 (standard window shell), ADR 0074 (layer "Sprache und Formate", BCP 47), ADR 0057 (words), `fs-components-words/DESIGN.md`. Everything marked **[open]** needs a decision; **[not verified]** was not checked.

## 1. What is there today (evidence)

**Words.** `fs-components-words` exists (`Words`, `Catalog`, `Fallback`, template language, `Cargo.toml` std only) but **no crate uses it**: `grep fs_components_words` finds only its own tests and example. Every widget and workbench has a `*Labels` struct with an English `Default` (20 structs, 19 `impl Default`; about 694 `pub ...: String` fields in 91 files of the component crates, an upper bound because it also counts non-label fields). Programs fill these in. `fs-components-app` says of itself "It brings no words" (`crates/fs-components-app/src/lib.rs:5-6`).

**Language is decided three different ways, and the shell does not know it:**

| Program | How it reads the language | Where |
|---|---|---|
| Store | `FS_LANG`, then `LANG` (no `LC_*`); only ~23 functions `fn x(lang: Lang)` have German, the rest of the window is English | `fs-store-core/src/language.rs:13`, `fs-store-app/src/words_lang.rs:3-22` (its own doc says "the rest of the window is English") |
| Wiki | `--lang`, else `LC_ALL`, `LC_MESSAGES`, `LANG` starting with `de` (`is_german`); a second copy of the same rule for the page language | `fs-wiki-app/src/frontend.rs:134-142`, `mode_read.rs:175-185`; German only for the reader labels (15 fields, `frontend.rs` `german_words`) and the menu words (`frontend_window.rs:34-38`); program name and "Search pages" stay English (`mode_reader.rs:73,89`, `mode_read.rs:125`) |
| Tasks | none; all English (`words.rs` header: "translation will replace this file's content") | `fs-tasks-app/src/words.rs` (33 constants) |
| Files, People, Groups, Calendar, Maps, Whiteboard | no environment read found [not verified further] | grep for `"LANG"`/`"LC_ALL"`/`"FS_LANG"` over their `crates/` |

**The mixture the person saw is built in:** the Store menu bar is `Menu::new(words::MENU_STORE ...)` (English constant "Store"), `words_lang::menu_view(lang)` ("View"/"Ansicht" by language) and `words::MENU_HELP` (English constant "Help") side by side (`fs-store-app/src/view/menu.rs:69-82`). With `LANG=de` the bar reads "Store | Ansicht | Help".

**Language is not remembered anywhere**: no `language` setting exists in any program (the three settings stores are: Store `settings.toml` with key `face`; Tasks a JSON file with key `frontend`, written atomically, `fs-tasks-app/src/frontend.rs:70-125`; Wiki a plain text file `frontend`, written aside and renamed, `fs-wiki-app/src/frontend.rs:63-110`).

**Menus today (B-M):** `Menu`/`MenuEntry` are plain values; `Shell::set_menus(menus, handler)` is the only door (`fs-components-app/src/shell.rs:98-113`, `menu.rs`). A `MenuEntry` has no check mark and a menu has no sections or submenus; `menu_view.rs` draws one flat panel per menu. The shell builds **no standard menu**: ADR 0065's Program/View/Help does not exist in code; each program builds its own:

- Wiki: menus Program (Quit) and View with one line per frontend, label `"✓ Frontend: Notion"` (mark typed into the text) (`fs-wiki-app/src/frontend_window.rs:33-57`).
- Store: Store, View, Help; View lists the frontends as `"● Frontend: Storefront (tiles or a table, Craft look)"` (`view/menu.rs:57-82`, `words_lang.rs:77-93`). The code still says "Face" (`enum Face`, key `face`, `face_line`), against the word rule.
- Tasks: a **top-level menu "Frontend"** next to Task and View; the shown frontend is `disabled()` instead of marked (`fs-tasks-app/src/frontends.rs:201-225`). The View menu there is the workbench views (List, Status), a different thing.

Three programs, three shapes. The choice is remembered in three formats.

## 2. Language (B-L)

Decisions of the strategy (2026-11-13) that this section follows: texts are **Unicode MessageFormat 2** files read with the `mf2` library behind the `Words` trait (ADR 0057); one language setting shared by all programs plus an optional override per program; the order of the chain below; the desktop portal is not asked in V1.

### 2.1 Built in step 1 (this branch)
Two crates, both with tests:

- **`fs-components-words`** (still std only): `Locale` (BCP 47 parser and normal form `de-AT`, `zh-Hans-CN`; `from_posix` for `de_DE.UTF-8@euro`; `chain()` = `zh-Hans-CN`, `zh-Hans`, `zh`), `resolve(program, shared, env, supported) -> Chosen { locale, source }`, the trait `Env` (`ProcessEnv`, a `HashMap` for tests, so no test reads the real environment), `LanguageSetting` (read; write atomically), the trait `Localized { fn for_locale(&Locale) -> Self }` for the `*Labels` structs, and `Args::iter`.
- **`fs-components-mf2`** (new; the only crate that depends on `mf2`, so the words crate stays free of it): `Mf2Texts::new(&[Source], &Locale)` is a `Words` over the chain (`de-AT`, `de`, `en`); `check_pairs(&[Source])` is the build-time check; `Source { language, text }` is made with `include_str!` today and from a downloaded language package later (it does not know where text comes from, so embedding now and loading later (ADR 0036) use the same interface).

**The chain, as built** (`resolve`, `tests/resolve.rs`, each link tested to win over the later ones and to be skipped when empty): the program's own override > the shared setting > `FS_LANG` > `LC_ALL` > `LC_MESSAGES` > `LANGUAGE` (GNU list `pl:de:en`: the first entry whose language is supported) > `LANG` > `en`. `C`, `POSIX`, empty and malformed values are no language and the chain goes on. **Portal: not asked in V1** (**[open]**: ADR 0074 names only the `org.freedesktop.appearance` keys; a language key is not known and was not checked; a desktop session normally exports `LANG`).

**The settings (two files, same format: one line, a BCP 47 tag, written to a temporary file beside it, synced, renamed).**
- Shared by all programs: `$XDG_CONFIG_HOME/freesynergy/language`, else `$HOME/.config/freesynergy/language`.
- Override of one program: `$XDG_CONFIG_HOME/freesynergy/<program>/language`, else `$HOME/.config/freesynergy/<program>/language` (strategy decision 2026-11-13: both below the configuration folder, as both are a person's choice; the program name must be `a-z`, `0-9`, `-`, so it can never become a path).
Evidence: no shared FreeSynergy configuration existed in the repos before (a search of `fs-*/crates` finds `XDG_CONFIG_HOME` only in `fs-components-app/src/window.rs:86`, where KDE's `kdeglobals` is read); the programs keep their own *state* under `$XDG_DATA_HOME/freesynergy/<program>/` (hub: `fs-hub/crates/fs-hub/src/daemon/config.rs:12,33`; Tasks `data_dir_in`; Wiki `settings_file`). A relative `$XDG_*` or `$HOME` is ignored (XDG rule; tested). A missing file is "no setting". An unreadable, oversized (more than 64 bytes, read with a limit), not-text, not-a-regular-file or broken file is an error: **`load_and_resolve` is the one place that reports it and goes on down the chain**, so every caller treats it the same (tested with both files broken). `save` writes a new file beside the old one with `create_new` (a planted link at the temporary name is replaced, never written through; tested), syncs it, renames it over the old one and syncs the folder.

### 2.2 The format: MessageFormat 2, and why not the others
- **Why MF2 (ADR 0057, Nutzerentscheid 2026-11-07):** it is the Unicode standard (ADR 0014 "Standards zuerst" counts it as first choice), translation files survive any change of library, plural forms and number formats come from the language, not from our code. The Unicode MF2 **specification** is the standard; the file around messages is not part of it.
- **Considered and not chosen: Project Fluent** (`fluent-bundle`, Apache-2.0 or MIT; mature, `.ftl` has standard tools but is no Unicode standard). It was built first in this branch (a working adapter and pairing check) and removed when ADR 0057 was pointed out; ADR 0057 itself records that `.ftl` files cannot be used unchanged as MF2. **Not chosen: a macro `texts!{}` of our own** (no translator tool understands it).
- **File format** (our container; MF2 has none): one file per language, `texts/en.mf2`, `texts/de.mf2`, next to the code that shows the text. Lines `id = message`; a message continues on indented lines; `#` comments. An id is letters, digits, `-`, `_`, `.`. Example in this branch: `crates/fs-components-widgets/src/message_composer/texts/{en,de}.mf2`. A plural is MF2's own: `.input {$n :number} .match $n one {{{$n} file}} * {{{$n} files}}`.
- **Result of a probe** (`fs-components-mf2/tests/texts.rs`): plural en/de (1 file, 3 files; 1 Datei, 0 Dateien), localized numbers (`1,234.50 euros` against `1.234,50 Euro`), escapes, missing value becomes a missing text (never a hole), de-AT uses de, `fr` without a file comes in English.

**The reservations of ADR 0057, checked** (source of the library: `~/.cargo/registry`, version 3.0.0, read in this run; the repository and the network were not visited):
| Reservation | Finding |
|---|---|
| Licence | `mf2`, `mf2-locale-data`: `MIT AND Unicode-3.0`; `mf2-catalog`, `-syntax`, `-runtime`, `-model`, `-macros`, `-host-std`, `-fn-number`: `MIT`. All permissive; `LICENSE` and `LICENSE-UNICODE` are in the package. **Reported:** `MIT AND Unicode-3.0` means both texts must be shipped with a binary (attribution); to be added to the licence list of the release. |
| Pinned | `mf2 = "=3.0.0"` in `crates/fs-components-mf2/Cargo.toml`; the package's own `.cargo_vcs_info.json` names commit `d598787b23e5c7841dd2a021ae2beffef32303c8`. Every sub-crate is `=3.0.0` inside `mf2`. `Cargo.lock` pins the rest. |
| Age, one author | Not re-measured here (no network); the ADR says since 2026-09 and one author. The crate is big for what we use: the product is aimed at Leptos and Ratatui; we use only `compile` + `host-std` + `number`. **Risk stays: maintenance by one person**; the interface (`Words`, `Source`) is cut so that the library can be replaced without touching a caller. |
| Test-suite claim | The published package does **not** contain the official MF2 conformance suite (README and source name `conformance/` of the repository, which is not in the package). **Not run**; the official suite (`message-format-wg`) was not fetched (no network by rule). What was run: our probe above. **[open]: an agent with network permission fetches the suite and runs it once.** |
| API fit | `mf2` is built around compiled binary catalogs (`tr!`, `mf2-build`); we use the plain path `compile_str` (one message per catalog, "for servers and tests" in its own docs), compiling each message when it is first asked for and keeping it. Works; it is not the path the author optimises. The cost per first call is not measured. |
| Blinc, Leptos | `mf2` names Leptos, Ratatui and a command line, not Blinc: no problem found, since the formatter is plain Rust (`no_std` core, `forbid(unsafe_code)`). |
| ICU4X | Not used for plural, numbers and dates: `mf2-locale-data` carries CLDR 48.2 data for plural rules and number symbols itself (probe passes). Dates: neutral `YYYY-MM-DD` and `HH:MM` (UTC) as in `fs-components-words`; the `datetime` feature of `mf2` (ICU4X) is **not switched on** (open). |
| Embedded or loaded | Embedded now (`include_str!`); a language package later makes a `Source` from a file. Both go through `Mf2Texts::new`. |
| Right to left | The bidi isolation marks around inserted values are switched off (`BidiStrategy::None`): the default put U+2068/U+2069 around every value, which shows as boxes in fonts that lack them. Needed again for Arabic and Hebrew: **[open]**. |

New dependencies, with reasons: `mf2 =3.0.0` (the decided library, features `compile`, `host-std`, `number`) and its nine `mf2-*` crates, only in `fs-components-mf2` and through it in `fs-components-widgets`. `fs-components-widgets` now depends on `fs-components-words` and `fs-components-mf2`.

### 2.3 Both languages are a must
- `check_pairs(SOURCES)`: every id in `en` and in `de`, the same variables (found by `mf2`, not by wording), every message compiles, no id twice, no empty message, an `en` and a `de` source exist. Each crate with texts runs it as one test (`tests/composer_texts.rs`: `assert_eq!(check_pairs(TEXTS), [])`); that is the build-time check (a failing test stops the build of the release). Every rule is tested to fire on its fault and to stay quiet on the good case (`fs-components-mf2/tests/texts.rs`).
- `contract/texts-check` R3 does the same over all `.mf2` files without cargo, plus "de equals en" (list the id under `[same]`).
- **Not done:** a `build.rs` (a test is enough to stop a release and costs no build time in every crate).

### 2.4 `*Labels` structs
The public API stays. Each `*Labels` gets `Localized::for_locale`; its `Default` is `for_locale(en)`. **Migrated as the example: `message_composer::Labels` (8 words)**; the English output is asserted equal to the old strings (`tests/composer_texts.rs`), German is asserted different in every field. The old `{}` slots for a reason stay (`for_locale` fills the MF2 variable `$reason` with the text `{}`), so no caller changes; once callers take `Words` directly the slot goes away. 19 structs remain (list in section 5).

### 2.5 Changing the language while the program runs
Menus change at once (the shell owns them). Widgets hold their labels from construction, so they change **at the next start**; the status line says so (strategy default 3). A live switch needs `set_labels` on each widget: later.

### 2.6 The Language entry in the shell (built in step 2)
Menu **Program > Language** (de: "Sprache") is a **submenu**: "System language (default)" ("Systemsprache (Standard)"), then one line per language the program has texts for, each in its own language ("Deutsch", "English"; the names are `language-name-*` entries of the `.mf2` files, never translated), the one set marked. **A choice in this menu is the program's own override** (`Scope::Program`: the file `$XDG_CONFIG_HOME/freesynergy/<program>/language`); "System language" removes that file, so the shared setting and then the environment answer. Reason: a person who changes the language inside one program means that program; changing it for all is a different act and belongs on the settings page.
**The interface for the settings page** (Nutzerwunsch "Sprache in den Settings"): the trait `LanguageControl` (`available`, `current(scope)`, `resolve`, `choose(scope, choice)`) with `Scope::{Program, AllPrograms}` and the implementation `FileLanguageControl` over the two files. The menu and the settings page of the admin frontend hold the **same object**, so they cannot disagree; the page calls `choose(Scope::AllPrograms, ..)` (tested in `standard_menus.rs`). The page itself is not built.
**Width and names (step 2c):** the panel of a next level is as wide as its longest line (the widest label measured with the menus' font plus paddings, mark column and arrow; at least 140, at most 360 px, never wider than the window less 2 x 8 px), so "Systemsprache (Standard)" no longer wraps (tested in both languages, also with the longer "Wie alle Programme (English)"; mutation: a fixed 140 px turns it red). The main panel keeps its fixed 220 px. The arrow on the line that opens a level points to the side it opens to (`folds_left`, one rule for place and arrow). The line says `aria-expanded` while its level is open (the overlay content reads the state, and the stack draws all entries again when the level opens or closes; the element is unit-tested, the redraw in a running window is not). A frontend with a translated display name brings it: `FrontendItem::named_in("de", ..)`, the menu takes the most specific name of the chain (`de-AT`, `de`), else the plain label; proper names (Storefront, Compact) may stay. **Gate:** test and example files are skipped by `contract/texts-check`, except those with a comment `texts-check: scan`; the picture test carries it, so a hard coded English menu word in the demo window is a finding (selftest: marked file with `MenuEntry::new("tiles", "Tiles")` is found, the same file unmarked or with a word from `.mf2` is not); the demo's words are in `tests/demo_texts/{en,de}.mf2`.
**The system line:** it is the line "no choice of my own" and carries the check then. If the setting shared by all programs holds a language, that one answers first, so the line reads "Like all programs (Deutsch)" ("Wie alle Programme (English)") instead of promising the system language; choosing it still removes the program's own choice (decided small in step 2b; tested). **Refused by the shell:** a view whose id starts with `fs.` (it would be taken for a language or frontend: `AppError::ReservedMenuId`), an active frontend that is not in the list (`AppError::UnknownFrontend`). **Left to the program:** `Resolved::problems` (a broken language file) is reported by the program, not by the shell: show it once in the status line.
**Switching:** the file is written, then the menus are made again at once (the bar and every line change language, tested), the status line says in the new language that the rest of the window changes at the next start, and the program gets `on_language(&Locale)`. A failed write is a visible problem (status line, red) and changes nothing.

## 3. The gate (B-L)

`contract/texts-check` (Python, standard library only, pattern of `contract/check`; `--selftest` runs a mutation check). Three rules (R3 changed with ADR 0057: it reads `.mf2` files, not a macro):

- **R1** hard-coded UI text: a string literal given to `text(`, `label(`, `title(`, `tooltip(`, `placeholder(`, `Menu::new(`, `MenuEntry::new(`, `Status::Info/Problem(` or assigned `= "..".into()` outside a `#[cfg(test)]` module.
- **R2** single-language table: in files named `words*`, `labels*`, `lang*`, a UI literal (these tables move to `.mf2`).
- **R3** `.mf2` files: a folder with `en.mf2` and `de.mf2`; every id in both, equal `$variables`, no empty message, `de` differs from `en` unless the id is under `[same]`.

"UI text" is a heuristic: has a letter, is no path, option, identifier or `fs-` name, and has a space or a capital first letter. An accepted case goes into `contract/texts-exceptions.toml` (`[literal]` key `file:text`, `[same]` key the message id) **with a reason**, as `contract/exceptions.toml` does. It finds candidates; a person judges.

**Run on the four trees today** (`contract/texts-check <tree>`): components 458 (R1 1, R2 457), Store 295 (1, 294), Wiki 34 (4, 30), Tasks 49 (4, 45); R3 0 everywhere (no `.mf2` file existed before step 1). After the first migration the components show R2 449 (was 457; the composer's 8 words left the table); Mutation self-test: now 12 of 12. Part of R2 is noise (date patterns like `'%I %p'` in `fs-components-charts/src/labels.rs:36-38`, which belong under `[literal]`, or better in the locale formats, ADR 0074 "Formate").  **Not covered, named:** texts built from pieces (`format!("{} files", n)` is neither R1 nor R2: the plural rule of the words crate must replace it, found by review), text in `.css`/`.toml`/`.xml` catalogs, text drawn by Blinc widgets of a dependency, a UI call with another name than the list. The list grows with each miss.

Strategy default 7: the gate runs in CI **as a warning** until step 6 is done, then it is hard (exit 1).

## 4. The Frontends menu (B-M)

### 4.1 Meaning
**Frontends** (de: "Frontends", the same word) are the layouts of the program (Store: Storefront, Compact; Wiki: Classic, Confluence, Notion; Tasks: Classic, Board, Day list). **Views** (de: "Ansichten": tiles, list, table, status) stay what the program offers inside one frontend. Strategy decision 2026-11-13: in the menu **View** (de: "Ansicht") the program's own views come first, separate from them stands one entry **Frontends** that opens a **submenu**: one line per loaded frontend, the active one marked (a choice, not a disabled line: Tasks disables it today, which reads as "not available"), a click switches.

### 4.2 API of the shell, as built (`fs-components-app`, step 2; `Menu`, `MenuEntry` are `#[non_exhaustive]`)
- `MenuEntry::checked(bool)`: the mark (a check, in a column the shell reserves for a group that has one) is drawn by the shell; the label stays the plain name; `role` is `menuitemradio`, `aria-checked` is set. `MenuEntry::submenu(id, label, children)` is a line with a next level (`children`); it is no choice (the handler never gets its id, `choose` returns `false`), `aria-haspopup`/`aria-expanded` are set, a small arrow shows. Ids stay unique across all levels.
- `AppWidget::set_standard_menus(StandardMenus, StandardCallbacks)`: **Program** = Settings, Language (submenu), Quit; **View** = the program's own views (`StandardMenus::views`), then **Frontends** (submenu, active one checked); **Help** = Help, About. Words: the shell's own, `texts/{en,de}.mf2`, in `StandardMenus::locale`, so a bar is never half German (strategy default 2). `Quit` is answered by the shell (`quit()`); Settings, Help, About and the program's views go to `on_entry` (ids `fs.settings`, `fs.help`, `fs.about`, and the program's own); a frontend goes to `on_frontend(id)` after the shell has moved the mark.
- `AppWidget::set_frontends(items, active, on_choose)` and `set_active_frontend(id)`: the frontends changed (a plugin was loaded or removed) or the program switched by itself: the submenu is made again. `FrontendItem { id, label, disabled }`.
- **Views and frontends are two things** (tested): the views are plain lines at the top of View; Frontends is one line below them that opens the next level.
- **Next level:** a press on a line with children opens the panel of the next level as **an overlay of its own** at the right edge of that line, level with it (the line's own bounds are the anchor, no estimate); a second press closes it, a press outside closes both, Escape closes the top one. Why two overlays: Blinc moves an overlay that would cross the right edge of the window to the left (margin 8 px); one 440 px overlay for both panels moved the panel away from its menu entry in a 640 px window (found in the review of step 2: `Ansicht` at 193 instead of 294). Now only the next level is moved: it stands on the right of the panel, or **folds to the left** of it where the window ends first, and is kept inside the window where neither side has room (then it overlaps the panel, as Blinc keeps any overlay). `tests/standard_position.rs` (640 px, three menus, German and English, panel x equals entry x; 800, 640 and 520 px with the next level inside the window; the fold; mutation: the old one-overlay build makes all three tests red). **Not built:** opening on hover, the Left/Right keys on the second level, a third level.

### 4.4 How each program feeds it (merge of the three shapes)
- Wiki: `Frontend::ALL`, label = name (no "Frontend: " prefix, no typed mark) -> `set_frontends`; replaces `menus()` in `frontend_window.rs:33-57`; `german: bool` goes away.
- Store: `Face::ALL` -> `set_frontends`; `view/menu.rs:57-82` shrinks to the program's own views (Programs, Sources, Settings, Messages); rename `Face` to `Frontend` with settings key migration like Tasks' `face` -> `frontend` (step 6, with the Store). **First migration to take, marked (strategy): the fixed `"Store"` and `"Help"` of `fs-store-app/src/view/menu.rs:69-82` (`words::MENU_STORE`, `words::MENU_HELP`, English constants next to the language-aware `menu_view`) come from `.mf2` files in Store 0.0.17**, so with `LANG=de` the bar reads "Store | Ansicht | Hilfe" at worst and "Programm | Ansicht | Hilfe" with the shell's standard menus.
- Tasks: the top-level "Frontend" menu (`frontends.rs:209`) goes; its entries go to View > Frontends; its classic View (List, Status) stays as the program's views.
- Programs with one frontend today (Files, People, Groups, Calendar, Maps, Whiteboard, Messenger): one line, `set_frontends` with a single item [not verified: whether their code can list a second].
"Loaded" (hot plugins, ADR 0074 section 8): the list comes from the program as data; when the store installs or removes a frontend package the program calls `set_frontends` again, and the menu is rebuilt (set_menus already rebuilds and closes an open menu).
