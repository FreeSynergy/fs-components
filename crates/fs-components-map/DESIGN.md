# fs-components-map - Design

The component *Karte* of ADR 0066: everything that shows a map lives here, no program draws one. A program gives markers ([`MapData`]) and, if it has them, vector tiles as bytes ([`TileBytes`]); the crate decodes (MVT), plans, draws and puts the view into the window shell as a `Surface`.

Moved here from `fs-components-widgets/src/map_view` (branch `maps-gui`, wip, 2026-11-06) and checked: its 18 tests pass, now in this crate. The crate has 45 tests now (math 13, ui 6, mvt 3, guard 13, memory 1, loading 9), and one more that writes the fuzz corpus (ignored).

## Pattern map

| Where | Pattern | Why |
|---|---|---|
| `mercator.rs`, `position.rs`, `tiles.rs`, `command.rs` | none (pure arithmetic) | Web-Mercator maths, no graphics, tested with extreme values |
| `model.rs` | Value objects | neutral geometry per tile; no tile format, no colours of its own |
| `choose.rs`, `place.rs`, `scene.rs` | Specification / Value | what is drawn within budgets, what is where |
| `draw.rs` | Adapter | the only code that touches Blinc's canvas |
| `widget.rs` `MapView` | Adapter + Facade | position, tiles, markers in; element out; holds no state |
| `keys.rs` | Adapter + Guard | same rule as `fs-components-widgets::keys` (its binder is not public) |
| `mvt.rs` | Adapter + Strategy | `mvt-reader` behind `decode_tile`; the look of a layer by its name |
| `surface.rs` `MapSurface` | Strategy consumer + Observer | `MapData`, `TileBytes` from the caller; `Live` draws again |
| `loader.rs` | Object pool with a lease + State per tile | places for fetching, time limits, tiles no longer wanted, failures, what is kept |
| `guard.rs` | Guard | a tile is scanned (bytes, features, rings x numbers) before `mvt-reader` decodes it |

## Tiles: limits (review of 2026-11-10)

* **Before decoding** (`guard.rs`): `mvt-reader` 2.5.0 (`parse_geometry`) reserves a buffer of the whole geometry of a feature (`G` numbers, 8 bytes a point) at the start, at every `ClosePath` and at every `MoveTo` of a line, so a feature costs `(commands + 1) x G` points, and what a layer decodes stays until the layer is done: the cost of a tile is the **sum over all its features and layers**. Running out of memory is no panic that `catch_unwind` catches. A tile is scanned in its raw protobuf first, with almost no allocation: at most `MAX_TILE_BYTES` (4 MiB), `MAX_FEATURES` (100 000) and `MAX_TILE_MEMORY` (64 MiB, estimated) summed over the tile: the geometry buffers (`ClosePath` and `MoveTo` both counted, numbers read as `u32` like the decoder, which cuts a longer number to its low 32 bits: a command head `(1<<32)|9` is the number 9 for it) **and the tags**: `parse_tags` copies the key and the value of every tag pair for every feature, so a 1 MB value string named by 400 features is 400 MB (with 4 MiB and 100 000 features about 300 GB); the guard adds, per tag pair, the key length, the value message length and `TAG_BYTES` (192 bytes: the map entry and what the map keeps free; 115 to 130 measured on the pairs of the review, `tests/memory.rs` "H mix" takes about 150 bytes for every pair together with everything else of its tile). Over a limit: `MvtError`, no decode. Evidence, with no memory used: the real bomb (`LineTo` + `ClosePath` x 250 000, 1 MB) is one feature of 1 000 003 numbers with 250 000 `ClosePath`, so `mvt-reader` would reserve 250 000 buffers of 1 000 003 points, 2 TB; the estimate says 2e12 bytes against 64 MiB. Tests: that bomb, the same bomb with the head `(1<<32)|9` of every command, a `MoveTo` bomb, 400 features that are each fine alone and over the limit together, and the tag bomb (one 1 MB value, 400 point features that name it), and the feature type `(1<<32)|2` (3000 x `MoveTo(1)`, 9 KB of input: the decoder reads the type as a 32-bit number and takes it for a line, 216 352 621 bytes taken when the guard did not cut it, 59 bytes now). Every number of a tile is cut to its low 32 bits in one helper (`wire::low32`): commands, coordinates, tags, the type of a feature and the extent of a layer.
* **The rule: no byte of input makes more than `BUDGET_PER_BYTE` (4096) bytes of memory, and no tile more than `MAX_TILE_MEMORY` (64 MiB).** The budget of a tile is `min(MAX_TILE_MEMORY, BUDGET_BASE (64 KiB) + BUDGET_PER_BYTE x bytes)`. The guard adds up, before anything is decoded, what the decoder will make: the geometry buffers, the copies of the tags, every point as a struct of its own (64 bytes), every layer (512), key and value (128 + its text) and feature (256), and refuses the tile over the budget (an `MvtError`, an empty tile for the surface, no panic). The number is high because `mvt-reader` reserves a geometry-long buffer for every `ClosePath` (and for every `MoveTo` of a line, not of a polygon): a polygon of 300 holes of nine points is 6.3 KB of input, the guard estimates 15 MB for it and the tile decodes (a test requires it). **How far the rule is proved:** the estimate counts the copy of the input twice, 12 bytes for every number of a geometry or of the tags (`prost`), 20 more for the numbers of a geometry (the output), 192 bytes a tag (measured 115 to 130) and 64 bytes a point; it is an upper bound as far as it was measured, not a proof: `tests/memory.rs` decodes tiles that are accepted and near the budget (the mix of probe H, 3000 to 4400 features, taking 26 to 36 MB where the estimate allowed 67 MB, and the larger ones refused) and requires `peak <= budget` for every accepted one; the fuzz target checks the same on any input. Small tiles of many lines reach about 3 300 bytes a byte; 4096 leaves a reserve above that. The claim "no tile more than 64 MiB" is the budget; the peak measured is lower for every tile tried. Tiles are decoded **one at a time in the whole process** (`loader.rs`, a lock), so eight workers that return together do not take eight budgets. Limits besides: `MAX_LAYERS` (256), `MAX_STRINGS` (100 000 keys and values), `MAX_FEATURES`, `MAX_TILE_BYTES`. The text of a label is shared by all points of its feature (`Arc<str>`): 20 000 points with a 1 MiB name took 21 GB before, now 4.9 MB (measured).
* **Evidence and fuzzing.** `tests/memory.rs` measures `decode_tile` with a counting allocator on the bombs of the reviews at their real size (a megabyte each: `ClosePath` x 250 000, `MoveTo` x 250 000, the head `(1<<32)|9`, a 1 MB value named by 400 features, 2000 and 20 000 points with a 1 MiB name, 550 000 empty layers, values and keys) and on ordinary tiles; the bombs are refused with a peak of at most 1 MB. `tests/bombs/mod.rs` builds them. The fuzz target `fuzz/fuzz_targets/mvt_decode.rs` (cargo-fuzz; its own `Cargo.toml`, outside the workspace) runs `decode_tile` on any bytes with the same counting allocator and fails when a tile takes more than its budget (the copies of the input are in it) or panics. Starting corpus `fuzz/corpus/mvt_decode` (scaled-down bombs and small tiles; written by `cargo test -p fs-components-map --test guard -- --ignored write_the_fuzz_corpus`). **Run it only under a memory limit**: `limited.sh -m 1G cargo fuzz run mvt_decode --manifest-path crates/fs-components-map/fuzz/Cargo.toml -- -rss_limit_mb=1024 -max_total_time=300` (cargo-fuzz needs `cargo install cargo-fuzz` and a nightly toolchain; run on 2026-11-11 with cargo-fuzz 0.13.2 and nightly 1.102: 300 s, 201 950 runs, no finding, under `-m 1G`). Every test of the guard runs under `limited.sh -m 1G`, too.
* **One extent per layer**: the result has the extent of the widest layer and the coordinates of a layer with another extent are scaled to it.
* **Loading** (`loader.rs`): at most 4 fetches at once and 8 workers alive; a fetch over `Limits::load_timeout` (20 s) gives up its place and its tile is `Failed`; a tile that the view no longer needs gives up its place at the next draw; `Ok(None)` is kept for good, an error, a panic or bytes that do not decode are `Failed` and asked for again after `Limits::retry_after` (30 s); at most `Limits::most_kept` (256) tiles are kept, the oldest go. A watchdog thread of the loader (it ends with it) applies the time limits on time, with no draw needed, and has the view draw again. A fetch that hangs cannot be stopped (no thread can), so its late answer is thrown away and `MOST_IN_FLIGHT` bounds the threads: **when 8 workers hang, no tile is fetched until one comes back.** `MapSurface::source_stalled()` says so (the map has no words of its own: the program shows "the source does not answer" while it is true); `tiles_loading()` counts the places held. The thread is made with `thread::Builder`: no thread to be had is a failed tile, not a panic. `MapSurface::with_limits` sets other limits (tests).
* **Attribution**: `TileBytes::attribution()` gives who made the data (for OpenStreetMap "© OpenStreetMap contributors"); the map shows it in the lower right corner, id `<name>-attribution`, whenever it is `Some` (a program that has tiles gives it from the data it has; `MapView::attribution` does the same for a program that draws by itself).

## Unsupported (named, not faked)

* No mouse drag or wheel: pan and zoom are the buttons and the keys (gestures come from the frontend, ADR 0037).
* The look of layers is a table of layer names (Protomaps/Shortbread); no style files (MapLibre style) yet. Labels are the `name` property only.
* No raster tiles, no clustering of markers.
