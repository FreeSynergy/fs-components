# fs-components - Design

Shared UI components of FreeSynergy on Blinc 0.6 (released crates, `blinc_* = "0.6"`, resolved 0.6.0). Rules: ADR 0005 (a widget is the core of an app), 0009 (Blinc only behind our API), 0015 (no second GUI framework), 0037 (a workbench is open, gestures come from the frontend), 0043 (patterns, small files), 0049 (components first, only what the next program needs).

## State

Version 0.2.0 is tagged (breaking against 0.1.0: `DataSource` is `DocumentSource`, `.reader()` is `.with_reader(..)`, `Options` has fields for labels, export target and drafts). First consumer: the wiki app (`fs-wiki-app`). Since 0.2.0 (the workspace version is 0.3.0, untagged until the second reviewer has passed it; the fixes of that review are on the branch `fix-0.3`): the workbenches `tasks`, `calendar`, `people` and `file_manager` (with the `FilePicker`), the widgets `list-view`, `calendar-view`, `breadcrumb`, `file-tile`, `file-preview` and `task-card`, the shared `drafts` and `source_error` (moved down from the workbenches), `page_scroll` and `input_slots` (shared by the workbenches with a detail page or a form), the menus and status panel of `fs-components-app`, and the chat components with the hardened answer guard of `tool-call` (`tool_call/guard`, `clock`, `guard/refresh`). Changed by the review: a held key never answers a question and a disarmed question asks for one redraw only (never more, none if time cannot arm it); `ToolCallView::answer` refuses a decision whose `choice` differs from the option it names; `ListView` and `TileGrid` report nothing for a key that leads to the row already chosen (so an arrow at the edge opens no folder); the file manager leaves a name being typed alone (Delete, carry, put down, restore, choose, empty trash and a retry of an upload are not offered or do nothing while one is typed) and asks the source for no change its capabilities do not allow; a save without changes keeps a "gone" message in `calendar`. The pattern lines of the source files name only the patterns of ADR 0043 (coding rules, section 2) or `none` (plain data, constants, pure functions); tests say `Tests:`.

| `search-field` (primitive): adapter over `blinc_cn` input, text kept in shared state | done |
| `text-view` (widget): neutral model (`Block`, `Inline`, `Mark`); headings, paragraphs, lists (also task items; bullet close to its text), quotes (nesting depth guarded at 24), code, tables, rules, emphasis (italic, drawn as a rich text), strong, strike, code span, links, hard breaks; unknown things arrive as `Block::Plain` and are shown as text. Text with marks is a flow of runs that wrap (also inside a long word) | done |
| Glyphs: characters Blinc's default fonts lack (Indic and Thai scripts, many emoji and symbols outside Blinc's bundled emoji subset) are set in an installed font that has them (`text_view/fallback.rs`, `fontdb` + `ttf-parser`; colour-vector emoji fonts such as the system "Noto Color Emoji" cannot be drawn by Blinc, so the monochrome "Noto Emoji" and the symbol fonts are used). It applies to paragraphs, headings, list items, table cells, code, unmapped text and emphasis. **It does not apply to the labels of the tree (the Blinc tree takes no per-run font), so titles in those scripts are boxes there.** The earlier claim "469 characters, 0 missing" counted font *lookups* on this machine (198 of 469 needed the fallback, all found a font); it is not a statement about what is drawn on another machine. A character no installed font has stays a box and is announced while the document is shown (`Reader::glyph_notice()`, first 8 characters then "and N more", not replaced by other notices such as "Saved."); characters in titles of the list, which the Blinc tree cannot draw in a fallback font, are announced too. The Chinese/Japanese/Korean ranges are looked up as well (a block no installed font covers is given up after 8 misses). Cyrillic, Greek, CJK, Hebrew draw with the default fonts when the system has them. **Arabic is drawn but not in reading order or right-aligned** (Blinc has no bidirectional text); Devanagari draws with wide word gaps. **What a release needs:** system fonts that cover the scripts of its documents (for example the Noto Sans family, Noto Emoji, DejaVu Sans); on a machine with DejaVu only or no fonts, Hindi, Thai, Korean and CJK are boxes. We do not carry fonts in the release (size and licence are the owner's decision); the release notes must name them | done, with these limits |

| `avatar-group` (widget): adapter over the `blinc_cn` avatar group; neutral `Person` (key, name, picture, presence); initials from the first and last word with a letter or digit (zero-width and direction characters, symbols, emoji and flags are skipped, they draw blank or half-formed); at most `max` circles (never more than 50), the rest is one "+N" circle and stays available as `hidden()`; a picture that is missing or whose header is not a picture is not handed to Blinc, so the initials show; the `key` of a person is for the caller to find it again in `shown()`/`hidden()` (the group has no click callback) | done |
| `transfer-list` (widget): transfers given as data (`Transfer`: key, name, direction, state Queued/Running/Done/Failed(reason), done, total); progress bar (`blinc_cn` progress), size text, buttons by state (Cancel; Retry and Dismiss; Dismiss) that report `Outcome{key, action}` to the caller's callback. It moves nothing and remembers nothing; at most 100 rows drawn (`max_rows`), the rest is counted in a line; texts from `Labels`; names and failure reasons wrap (they must stay readable to the end); a failed transfer is always drawn even beyond `max_rows` (at most `max_rows` such late failures, the line then says how many failed ones are not shown) | done |
| `sortable-list` (widget): lanes of neutral `Item`s (key, label, locked); lanes may be closed to items from others. Pure move logic `Sorter` (cursor, one item held, carried live, dropped = `Outcome::Moved{item, from, to}`, cancelled = back exactly where it was); every step answers with an `Outcome`, also refusals (locked, closed lane, edge, empty, busy). Keyboard through optional `Bindings` (default: arrows, Home/End, PageUp/PageDown, Space or Enter pick up and drop, Escape gives up; Ctrl and Alt are never taken). Pointer/touch: the frontend calls `grab`, `hover`, `drop_grabbed`, `cancel`, `move_item`; no pointer gesture is wired in the widget except click = cursor. The widget keeps a copy of the lanes: the caller applies `Moved` to its data, and `set_lanes` takes the data back (also to undo a move it refused). Long lanes draw a window of at most `max_rows` (default 200) around the cursor with "N more above/below" lines. Row content may be replaced by the caller (`content`, type `sortable_list::Content`, also `SortableContent` at the crate root). A click on a row (also on its content) reports `Outcome::Chosen{item, source: Pointer}` and puts the cursor there; `Command::Open` (not bound by default; bind it to `Key::Activate` for "Enter opens, not picks up") reports the same with `source: Keyboard`, so a consumer can tell the two apart without any Blinc event, and `bind_keys` stays private (its broadcast guard cannot be bypassed) | done, see Not verified |
| `lightbox` (widget): neutral `Media` (key, source, caption, picture or not); pure `Viewer` (show, next, prev, first, last, optional wrap, set_items keeps the place by key); `LightBox` handle with a Blinc view: counter, Close/Previous/Next buttons (the edge button is greyed unless stepping wraps), the picture fitted inside the stage (Blinc image, `contain`, no crop), caption; optional `Bindings` (Left/Right/PageUp/PageDown step, Home/End jump, Escape closes). A picture path that is not a file, an item that is not a picture, and no items each show a note from `Labels`, never an empty stage. Does not open an overlay: the frontend places it at window size and removes it on `Outcome::Closed`. Not built: zoom and pan, video and other kinds (`Media::other` is announced), preloading of neighbours, touch swipe (a gesture: the frontend calls `command`) | done, see Not verified |
| `list-view` (widget): columns and rows from the caller through `RowSource` (`count`, `rows(first, limit)`, a failure is shown in place of the rows), fixed row height, only the rows in view exist as elements and are read a page at a time (8 pages of 64 kept). Selection reports the key through a callback; the caller draws it by `selected(key)`, and by not doing so refuses: then neither keys, clicks nor the scroll position move the cursor. Without `on_select` nobody can answer, and the keys move the list from the selected row. The keys know their row by key, so changed data is followed, and a row that is hidden gives a fresh start at the first row. `ListPosition` keeps the scroll place across rebuilds. Keys off by default, per widget through `keys::bind_keys`; they start from the selected row (`RowSource::position_of`). A row can carry a `mark`. A long text ends in an ellipsis (`fit_cell`, measured, Blinc has none). One derived list of rows per position, made outside any build's scope and given back with the position. Blinc's `virtual_list.rs` does not fit: it builds the first `window_size` rows once and a spacer, and never follows the scroll, so a scrolled list is blank. Used instead: what `blinc_cn`'s long select does (a box as tall as all rows, `for_each` over the window, `ScrollRef::watch_y`). 100,000 and 10,000,000 rows drawn offscreen; wheel, click and keys driven in-process through the router. Above about 500,000 rows of 32 px the positions are f32 with steps of 2 px and more (at 10 million: 32 px); nothing breaks but rows sit unevenly. | done |
| `calendar-view` (widget, provisional): month (six weeks), week and day on a time axis, agenda; items from the caller (`CalendarItem`: key, title, wall-clock start and end, all-day, marks, category colour), all words from the caller (`CalendarNames`), colours from theme variables only; overlapping items split sideways into lanes, lanes narrower than 56 px replaced by a count; items over midnight on each day they touch; a click reports `Picked::Day`, `More` or `Item`; a long agenda is windowed like `list-view` (5000 items: 105 ms to build and lay out in a debug build, was 7.5 s); below 420 px a month or week is drawn as the agenda; no lock and no `stateful`; the agenda's window of lines in view is a `Computed` over the scroll offset, as in `list-view`, and what a line shows comes from the items of the build, so a rebuild with other items of the same number shows those (tested). `blinc_cn`'s calendar does not fit: it is the date picker (fixed 252 px grid, English constants, three dots a day, no times). Not built: drag, resize, swipe, pinch, animation, keys on days and items, `role` | done, provisional |
| `calendar` (workbench, provisional): open like `people` (ADR 0037), embeds `calendar-view` (ADR 0005), knows no store and no `fs-calendar` type. `CalendarSource` (provisional: synchronous and on the interface thread), `CalendarLabels`, state machine `CalendarState` tested without a window, `CalendarWidget` with `build(w, h)`, `styles()`, `with_state` (closure only), `compact`. Same editing rules as `people`: unsaved changes block leaving, first Cancel asks, a failed save keeps the draft and Cancel reads again, a conflict's next Save writes knowingly, what is gone leaves the view, asking and confirming a delete are two actions in two places. Never opens an item on its own (ADR 0029). Every change is a full rebuild, with no live area. What is drawn is as of the last reading: a change made elsewhere shows after the next click on the item or move of the view. What cannot be read is named above the calendar and opens on a click (`ItemsRead::problems`), the rest stays. Discarding an edit is a second action in another place, like Delete; a save of something gone keeps the draft. Marks and the reason of a failed save stay out of the scroller. `context()` gives item, view and date back as a plain value (ADR 0056). Blinc note: a press reaches every ancestor and cannot be stopped, so an element reporting a day is never an ancestor of an item | done, provisional |
| `people` (workbench, provisional): open like the reader (ADR 0037), knows no store and no `fs-people` type. `PeopleSource` (provisional: synchronous and on the interface thread like `DocumentSource`): `capabilities`, `rows(term, offset, limit)`, `read` (neutral sections of labelled fields, marks), `draft`, `blank`, `save`, `create`, `delete`. The source reports no total: one row more than a page is asked for, and a More button loads the next 200. `PeopleLabels` holds every word. State machine `PeopleState`, tested without a window: selection, search (also during an edit), the reader's editing rules (unsaved changes block leaving, Cancel asks once, a refused save keeps the draft, a conflict changes nothing and the next Save writes knowingly), delete is two different actions tied to one person, so a double-click can never delete: what lies under the pointer after the first press keeps the person, and the deed is on a line of its own below the bar. Below 560 px the list stands above the person, each with the whole width, so it is reachable down to at least 160 px (tested). Errors kept and shown. Cancel and a Save without changes read the person and the list again; a person someone else deleted leaves the list. Rows carry marks in the source's words, also in search and the compact variant, and the form keeps showing them; a row marked `only_when_chosen` is never opened by the workbench, neither at the start nor after a delete (ADR 0029). `PeopleWidget`: `new`, `compact` (list and detail, no changes), `build(w, h)`, `with_state`, `refresh`, `styles`. A search redraws the list area, with its More button and its height, through a signal (the field keeps the keyboard); everything else is a full rebuild, so no `cn` element is built in a live area. More is therefore a plain element and a tab stop; the window turns Enter and Space on it into its click. A failed Show more keeps the rows, says why, and can be tried again. A source's `delete` may answer with a remark: the person is gone, but this must still be said. Views draw from a snapshot, so no lock is held while elements are built. Clicks, typing into the search field and the list are driven in-process through the router (`tests/people_widget.rs`); key presses in a form field and a real window are not tested. Search field and form use the small size. Closing the window loses a draft (`DraftStore` of the reader is not connected) | done, first version |
| `task-card` (widget, provisional): a card from a title, lines, tags and marks in the caller's words; plain element, no click of its own, no colours or words of its own. `board-column` is not built: a `Lane` of `sortable-list` is the column. `checklist` is not built: the first scope has no checklists | done, provisional |
| `tasks` (workbench, provisional): open like `people` and `calendar`, no window function (ADR 0056), knows no store and no `fs-tasks` type. One set of tasks as a list or by status (`TaskView`; the word "Status" comes from the caller). `TaskSource` (provisional: synchronous, on the interface thread), `TaskLabels`, state machine `TasksState` tested without a window, `TasksWidget` with `build(w, h)`, `styles()`, `with_state` (closure only), `compact` ("my next tasks": open tasks, list and detail, no changes), `context()` (plain value: the selected key and the view; provisional shape, ADR 0056). Same editing rules as `people`; a failed reload keeps what is drawn. Cancel with typed text only asks: Keep editing stands where Cancel was, Discard on a line of its own below the bar, as Really delete; `people` does the same. A save of a task deleted elsewhere keeps the draft. Moves: `TasksState::move_task` answers with a `MoveOutcome`, whichever way it came. The status view draws `sortable-list` lanes in a box that scrolls both ways (a column is never narrower than 190 px); keys are the list's (arrows, Space or Enter to pick up and put down, Escape), the cursor opens nothing, Open opens the card under it; a click on a card opens it (`Outcome::Chosen`); buttons per column beside the task are the pointer's way, at fixed places, the column it is in does nothing, so a double-click cannot go further than chosen. The view always says what moving does, and that a computed status becomes fixed. A hold is given up on leaving the view; while held, lanes and cards wait. In the list view the keys only walk (`ListView::walking`): the row stands out, nothing is read, Enter or a click opens. A failed move shows where the source has the card and says why. **Not wired: dragging with a mouse.** A gesture is the frontend's (ADR 0037): `TasksWidget` gives it `grab`, `hover`, `drop_held`, `cancel_held`, tested through that API only. A marked row: marked in list, card, sheet and form, never opened by the workbench; walking over it by keys shows nothing in either view. The detail pages of `people` and `tasks` scroll as a whole, buttons too (`page_scroll.rs`, one copy for `people`, `tasks` and `calendar`) | done, provisional |
| `breadcrumb`, `file-tile`, `file-preview` (widgets, provisional): neutral, no words or colours of their own. `Breadcrumb` keeps the first and last steps at any width and has plain steps that are tab stops; the last step is no button. `FileTile` is a plain element; `TileGrid` is the grid of them on `list-view`'s `ListPosition`, only the rows in view exist. `FilePreview` draws facts, marks outside the scroller, and text from `safe_text` (UTF-8 and no NUL, control and direction characters replaced, at most 200 lines of 200 characters) or a picture that passed `picture_fits` (PNG or JPEG header at most the given size) | done |
| `file_manager` (workbench, provisional): open like `tasks`, no window function (ADR 0056), knows no store and no `fs-files` type. `FileSource` (provisional: synchronous and on the interface thread), `FileLabels`, state machine `FilesState`, `FileManagerWidget`, `FilePicker` (compact, gives back `PickedFile`, ADR 0037), `context()` gives folder, selection and view as plain values. Folders as a tree (`tree.rs`) and a breadcrumb, what is in them as a list (`list-view`) or a grid (`file-tile`), one thing selected and shown (`select.rs`; a safe preview through `file-preview`; a marked file is read only when asked, ADR 0029; a key at the edge of the list opens nothing). Changes (new folder, rename, move, copy, restore; `command.rs`, `carry.rs`): a taken name asks (keep both only where the source can); Delete, purge, empty trash, download of a marked file, dropping an unfinished upload and choosing a marked file are two acts at two places (`confirm.rs`, `view/band.rs`); a name or path being typed is never thrown away by another act (`input.rs`: Cancel asks first, the other acts are not offered while one is typed). Upload and download by a path the person types, unfinished uploads, rescan, filter by size and date (`transfers.rs`, `filter.rs`). `FileCapabilities` decide what is offered and what the state does; the picker gets the read-only ones and changes nothing. Calls are synchronous and block the interface thread (provisional) | done, first version |
| `share-dialog` (widget): **only the dialog.** The Sharing interface does not exist yet (`Sharing` in the contracts is an empty placeholder), so there is **no stored right and no permission model here**. The caller gives `Choice`s (key, name, kind text, detail text: people, groups, anything) and `Permission`s (key, label: any names), and gets back one value, `Outcome::Confirmed(Vec<Grant{choice, permission}>)` (or `Cancelled`), through a callback. A new pair gets the first permission offered; no permissions offered means `permission: None`. Filter field (our `search-field`) narrows by name, kind and detail, case-insensitive; pairs hidden by the filter stay chosen and are confirmed (the count line says how many are chosen); pairs given as already chosen that are not in the offered list are kept and returned. `require_choice` makes an empty confirm a refusal. Rows drawn at most `max_rows` (100), the rest counted in a line. Optional `Bindings` (Up/Down, Space or Enter as `Activate` = choose/unchoose, Left/Right = permission, Escape = cancel; no default key confirms, because the window keeps Enter: Tab to the Done button and Enter or Space there). **Rights are never raised:** a permission in `choose(..)` is kept as given, also one that is not offered (shown as "Unknown: key", returned unchanged unless the person picks another); a new pair gets only the permission the caller names with `default_permission`, otherwise none, and Done is refused (`PermissionMissing`) while a pair has none. A pair whose choice is not offered is shown as its own row and can be removed (by click; not by keyboard). Permission buttons wrap. The frontend puts it in a modal; what a permission means and where it is saved is the caller's | done, see Not verified |
| Shared by the programs' frontends (`fs-components-app`): `write_new_file` and `write_new_private_file` (mode 0600 from the moment it exists) (export that appears whole or not at all, never replaces, moved from `fs-people-app` and `fs-calendar-app`), `parse_size` (`--size`) | done |
| `reader` (workbench): `DocumentSource` trait, `Labels` (all texts come from the caller), state machine `Reader` (open, follow, back, search, edit, export) | done |
| Embedding: `ReaderWidget::new(source, labels, export_target)` and `.build(w, h)` place the reader in a program's own window and layout; `.with_reader(|r| ..)` gives the state to menus and commands; `launch` makes a bare **app** (ADR 0056: an app is a workbench over the whole screen, with a menu and more parts; this one has neither, so it is for trying and for the simplest program; its proper place is `fs-components-app`, not moved yet because `fs-wiki-app` uses it at tag 0.2.0 and moving it breaks that); `snapshot` is a picture without a window | done |
| Editing: `DocumentSource::{can_edit(path), source_text -> EditableText{text, revision}, save(path, text, revision)}`. A save with an old revision is a `Conflict`: nothing is written, the draft stays and the reason is shown. Save without changes writes nothing. The text area cannot hold some text exactly (it drops a final newline, turns CRLF into LF): the draft is compared and saved in the form of the original (an untouched text is saved as the original, exactly), and what saving would change anyway (mixed line ends become one kind, blank lines at the end are dropped) is announced above the editor before the person saves. A final newline cannot be edited: Enter at the very end of a text that ends in a newline counts as no change. Unsaved changes block leaving the document and refuse `follow` (`Outcome::Blocked`). Cancel with unsaved changes asks first (second Cancel discards); Esc is not handled at all, so it can never throw a draft away. After a conflict the draft stays in view and the next Save replaces the other version knowingly. After a save the list, the title and the search results are read again; a failed list stays visible | done |
| Draft backup: `DraftStore` (host-supplied; the reader has no storage), `ReaderWidget::drafts(store)`. Written after 0.5 s without typing and at least every 5 s while typing, by a timer thread outside the reader's lock (`BackupJob`); a failed write is retried every 2 s and shown (the thread redraws when the message changes). An **offered** backup (found at the start of an edit) is not touched until the person answers: Restore (asks first if text was typed) or Discard (typed text is then backed up). A backup that names another document, or equals the document, is not offered (reported / removed). A document that changed since: Save reports it first (source revision, or once by the reader for a source without revisions). Discarding the newer text of the second slot offers the older backup that waited behind it. `Draft.path` is an opaque store key (the document path, or with a suffix for the second slot). Save and a chosen discard clear only a backup this edit wrote. **Closing the window does not drop the reader** (Blinc's global state keeps it), so a close loses at most the last pause | done |
| Export: `can_export(path)`, `export(path, target, overwrite)`; the target is chosen by the caller; a taken target is a `Conflict` and the reader asks (press Export again to replace; the confirmation belongs to that document and that target and is cleared by editing) | done |
| Scrolling: every column on the way down has `min_h(0)`; a long document is clipped and scrolls (3000 paragraphs draw). Tested offscreen with a scroll offset | done |
| Embedding keys: Alt+Left and Ctrl+S act on every reader in the window (keys are broadcast); `ReaderWidget::keys(false)` switches them off, the program then calls `with_reader` itself (state access is a closure: no lock can be held across calls) | done |
| Keyboard: tree keys (Blinc), Alt+Left back, Ctrl+S save, Tab to search field and buttons. Search results, links and the tree rows are **not** reachable by Tab (the Blinc tree is no Tab stop; links are click targets) | partly |
| `words` (crate `fs-components-words`, std only): translatable text, ADR 0057. `Words::say(TextId, Args) -> Said` (found, or missing with the id shown); `Args` of named `Value`s with a kind (Text, Count, Number, Date, Time; no finished strings); `PluralRules` per language (zero to other; English, Polish); template language (`{name}`, `{n, plural, one {# x} other {# y}}`, backslash escapes); `Catalog` (from a table or `id = template` lines), `English`, `Fallback` (a missing text comes in English). Unsupported: per-language number and date formatting, plural of fractions, exact `=N`, `select`, a Fluent/MF2 adapter. `labels.rs` unchanged. See the crate's `DESIGN.md` | done, first version |
| `charts` (widget, crate `fs-components-charts`): a Vega-Lite subset (see below), parsed, laid out and drawn; bar, line, area, point, arc; text alternative; theme colours checked for colour-blind readers | done, provisional (subset, numbers 3 / 15 / 8 / 10000 open) |
| Pointer cursor over links; scrolling to a `#fragment`; table column alignment; selecting text; images; accessibility | not built |

## Structure and pattern map (ADR 0043)

| Where | Pattern | Why |
|---|---|---|
| `widgets/text` | none | the neutral description (blocks hold blocks, marks are stand-off ranges in characters): plain data, `plain.rs` one fold over it |
| `widgets/text_view/blocks.rs` | Adapter | our block model in, Blinc elements out; a `match` on the block kind picks one drawing function; `Plain` is the safe fallback |
| `widgets/text_view/inline.rs` | Adapter | no marks: one Blinc rich text; marks: `flow.rs` |
| `widgets/text_view/flow.rs` | Adapter | text cut into runs of one style (word plus its spaces), each a small text element in a wrapping flex row; a link run has its own click handler and reports to the `LinkHandler` (Blinc's own link would open a browser) |
| `widgets/text_view/fallback.rs` | Facade over `fontdb` and `ttf-parser` | which installed font draws a character Blinc's fonts lack, looked up once and kept |
| `widgets/text_view/look.rs`, `*/styles.rs` | none | every colour and size read from the theme; style sheets are constants with theme variables only |
| `workbenches/reader/edit.rs` | State | `Editing` (original, draft, error) and its transitions |
| `widgets/avatar_group` | Adapter | `blinc_cn` avatar group behind `AvatarGroup`/`Person`; the people who do not fit are counted by Blinc's own "+N" circle (empty circles stand in for them) |
| `widgets/transfer_list` | Adapter + State + Observer | `blinc_cn` progress and buttons; the state decides the buttons; the callback is the outcome channel |
| `widgets/sortable_list/{state,moves,steps}` | State + Command | pure, no Blinc; `Command` is the one vocabulary for keys and gestures |
| `widgets/{sortable_list,lightbox,share_dialog}/bindings` | Value object | plain data: the keys and the step each names; optional and replaceable. `Command` has an `apply` (`steps.rs`, `handle.command`) but no `invert` |
| `widgets/sortable_list/{handle,view}` | Facade + Observer + Adapter | `SortableList` handle (clonable, no guard returned, copies out), outcome callback, Blinc view |
| `widgets/keys`, `widgets/live` | Adapter, Observer | `Key` is ours; `bind_keys` lets a key reach a handler only while that element has the keyboard (a broadcast reaches all handlers; two lists must never both move); `Live` redraws a view after a state change |
| `widgets/lightbox` | State + Command + Adapter | same shape as `sortable-list`: pure `Viewer`, optional `Bindings`, handle plus view; Blinc's image behind `Media` |
| `widgets/share_dialog` | State + Command + Adapter | pure `Sharing` state, optional `Bindings`, handle plus view; neutral `Choice`/`Permission`/`Grant`, no dependency on any program |
| `widgets/tree_view` | Adapter | `TreeNode` to the `blinc_cn` tree |
| `widgets/list_view` | Strategy (`RowSource`) + Adapter | the caller's rows read a page at a time; only the rows in view exist as elements, on Blinc's scroll container |
| `widgets/list_view/cache.rs` | Decorator | a few pages of rows kept over the `RowSource` |
| `widgets/list_view/position.rs`, `widgets/calendar_view/position.rs` | State | a handle the owner keeps, so scroll place and the row under the keyboard survive a rebuild |
| `widgets/calendar_view` | Adapter | pure layout (`layout.rs`) then plain Blinc elements; `view.rs` is the `CalendarView` widget (Adapter, part of it, no builder), `day.rs` the value types `Day` and `Moment` (no pattern of the table fits), `agenda.rs` a windowed list of lines |

## Decisions

* **Layers.** `search-field` is a primitive (one value). `text-view` and `tree-view` are widgets: they know their data model when built (blocks and marks, labels). The `reader` is a workbench (ADR 0049: a subset of component; ADR 0056: a workbench always returns a context to its host and does not run alone): it gets its content at run time through `DocumentSource` and does not know what it means. Provisional: the crate split per layer and the name `reader` (see Open points).
* **The theme decides.** No colour or font is written in code. Sizes and colours are read from `ThemeState`; stylesheets only use `var(--...)` of the theme. The shell builds the theme bundle from `blinc_cn::cn_bundle()` plus our sheets.
* **Links.** The text view only reports `href` as written. Resolving it (relative path, external) is the data source's `resolve`, so the workbench does not know what a link means.
* **Gestures** are not here (ADR 0037); clicks and keys are the plain events of the framework.
* **Offscreen picture** uses Blinc's own `BlincApp::render_tree` into a texture and a PNG. It draws the same view functions as the window, from the same `Reader` state; clicks are not simulated.

## Application shell and how a program uses it

Two crates beside the three layers (provisional, Thread 4 of the sprint):

* `fs-components-render`: `bundle(css)`, `register_fonts()`, `draw_to_png(canvas, build, after_layout, path)`. Knows no workbench and no app, so both may use it. Facade: one function keeps the order runtime, element, sheet, layout, draw, write; the caller supplies the element and an optional step after the layout. Variants of `RenderError` tell "no graphics adapter" from a real failure.
* `fs-components-app`: `Surface` (Strategy: anything the shell can draw), `Screen`, `Menu` and `MenuEntry` (Value objects; an entry is an id, one handler receives it; no operation enum, so no Command), `Shell` (State, no window needed), `AppWidget` (Facade + Observer: one signal per live area, so a status message does not rebuild the workbench), `launch`, `AppWidget::picture`. It holds no words and no colours: labels come from the program, colours from theme variables. Sizes the surface must be told are constants in `styles.rs`.

A program's frontend (ADR 0005, 0009, 0037) is a crate `fs-<program>-app` in the program's repo: arguments, opening the core, labels, `Screen`s. It imports no `blinc_*` crate. Its work surface is a workbench in `fs-components` (open, knows no store and no program core, takes a trait), so another program can embed it.

Menus (ADR 0005, ADR 0056 point 4): `AppWidget::set_menus(menus, handler)` puts them into the title bar, after the title; a long title gives way. No call, or only empty menus, means no menus and the bar as before. The menus, the handler and which menu is open are in `Shell`; `menu_view.rs` draws, `menu_overlay.rs` keeps Blinc's overlay stack in step, and the lock of the shell is never held while the stack is touched or the handler runs. An entry's id must be unique among all menus (`AppError::DuplicateMenuEntry`). A press on a line closes the menu first and then runs the handler; a disabled line does nothing and leaves the menu open; a line counts only while its menu is open, so a double-click chooses once. To change a label or disable an entry, call `set_menus` again. `AppWidget::choose(id)` does what a press does.

The keyboard is Blinc's own navigation, which walks elements by role: Tab reaches the first menu, Left and Right move between menus, Down opens on the first line and Up on the last, Up and Down skip disabled lines, Enter chooses, Escape closes and the keyboard returns to the menu, Left and Right in an open menu go to the neighbouring menu (with only one menu, this closes it).

`blinc_cn`'s `menubar` is not used, for three reasons: its dropdown does not close on a press outside (below), and neither its panel id nor its overlay handle is reachable to add that; which menu is open sits in its private signals, not in `Shell`; its lines have no ids a test could press. Kept from it: the overlay kind, the classes for the looks, the roles the keyboard needs, and closing before the handler runs.

Not built for menus: submenus, separators, shortcuts shown in a line, a mark on the menu that is open, scrolling (a menu taller than the window is cut off), and any way to show menus that do not fit a narrow bar (they are cut off). A press outside closes the menu and also does what it does there, on a navigation entry for example.

Blinc notes for menus (0.6.0): `cn::menubar`'s dropdown stays open after a press outside (seen through the router, and the window never calls `OverlayStack::handle_click_at`, found by reading). A panel that is closing can still be pressed for as long as its exit runs; without a guard the second press of a double-click ran the handler again (seen with our lines; `cn::menubar`'s lines have no such guard, found by reading). Every full rebuild forgets click-outside registrations (`clear_click_outside_handlers`, found by reading), so one made when a menu opens must be made again by the build.

Status line (ADR 0005): a text that does not fit ends in an ellipsis (`fit_cell`), and a press or Enter on it shows it whole in a panel of the same kind as the menus, above the line, which scrolls when the text is taller than the room. A second press, a press outside, Escape or a new message closes it. Tests through the router and the overlay stack in `tests/status_panel.rs`. `--size` is refused above 8192 on a side (`wgpu` panics there). `MIN_WINDOW` is 480 x 540, what a workbench with its list above its page needs; `min_surface()` is what a surface gets there with one screen, and the tests of `people` and `tasks` use it.

Not built in the shell: shortcuts for the navigation, window state across runs, compact variants, and a way to post to the interface thread from a worker (`select` and `set_status` must be called on it; a program with background work cannot report yet). Changing the screen is a full rebuild; only the status line is a live area. Tests open no window; `AppWidget::build`, which `launch` calls, is drawn offscreen and compared with `picture`. Menus are pressed and typed at through Blinc's router, hit test and overlay stack, in the order of its event loop (`tests/menu_common`), including an incremental rebuild; no menu has yet been used in a real window. `launch` ran once in a real Wayland window for 20 seconds without a crash or a log line (2026-11-06); that says it starts and keeps running, not that it looks right or reacts.

To try it by hand: `cargo run -p fs-components-app --example shell`. Check: the window shows the title, two navigation entries and the status line "Ready"; a click on "Second" changes the heading and the highlighted entry; Tab reaches the entries; resizing keeps the layout. Menus: "View" and "Help" in the title bar; "View" > "Second screen" changes the screen; "Help" > "About" writes to the status line; "Manual" is grey and does nothing; a press beside an open menu closes it; Tab, Down, Enter and Escape work as above. `cargo run -p fs-components-app --example shell -- /tmp/shell.png` draws a picture and opens no window.

## Public types and Blinc

* **Closed types are avoided:** public enums and structs that a later feature will extend are `#[non_exhaustive]` (`Block`, `MarkKind`, `Align`, `LinkTarget`, `Outcome`, `Shown`, `Step`, `ErrorKind`, `Entry`, `Hit`, `Document`, `Labels`, `Options`, `Picture`, ...) and come with constructors; build `Labels`/`Options` by `Default` and assigning fields.
* **Blinc in signatures:** the elements our functions return are Blinc elements, because a component is placed in a Blinc layout and a program that embeds the reader owns a Blinc window (ADR 0009: Blinc is the GUI). They appear only as `impl Element` (`TextView::build`, `SearchField::build`, `ReaderWidget::build`), and `Element` is one re-export in `fs-components-widgets`; no other Blinc type is public (data types are ours). Wrapping the trait in a newtype would copy its whole interface for no gain today; revisit when a second GUI backend is real.
* **Blocking:** `DocumentSource` is synchronous and the reader calls it **on the interface thread**; a slow source freezes the window while it works. This is provisional (a later version makes it async or runs calls on a worker). Numbers for the wiki are in `fs-wiki` DESIGN.md.
* **Closing the window loses the draft** of an unsaved edit: Blinc has no close hook (listed as a Blinc item). "Unsaved changes block leaving" means leaving a document, not the window.

Blinc notes (0.6.0; to be passed upstream by the owner, reproductions in the report of the first release):

* `widgets/virtual_list.rs` builds its first `window_size` rows once, with a spacer, and never follows the scroll. Found by reading the code. Used instead: what `blinc_cn`'s long select does (`for_each` over a computed window, `ScrollRef::watch_y`).
* What a window's build creates is owned by a scope and disposed when the next build replaces it (`owner::BuildScope`), so a signal or computed kept across builds dies silently unless made under `Owner::detached`: the list then stops following the wheel, with no error. A test harness without that scope sees the opposite, a graph that only grows (9 to 1,809 derived nodes in 200 rebuilds of the workbench): that was a harness without `BuildScope`, not a leak in a window. With the scope the harness of `tests/people_widget.rs` measures 9 derived nodes while reading and 25 in the form, flat over 30 rebuilds and 30 searches. Not measured in a real window.
* Elements built outside a build pass (a `stateful` callback building nested `stateful` or `cn` elements) get a new key each time, because `key::reset_call_counters` only runs at the start of a rebuild. `STATEFUL_DEPS` never shrinks, so the old callbacks keep running. Found by reading the code, not measured. Workaround in the shell: a change of screen is a full rebuild. A `ReaderWidget` rebuilt inside a live area would be affected.
* `State::update` only reaches a `stateful` through a callback that `BlincContextState::init` does not install, and the window skips its own init when a picture came first; `Signal::update` works in both orders. Found by reading the code.
* On the visual update path a live area's own node keeps the classes of its first drawing (`renderer/build/subtree.rs`), and a child without a handler keeps the handler of the node it replaces. Found by reading the code. Workaround for the classes: they sit on an inner element.
* `blinc_noto_emoji::register()` adds the font again on each call (its doc says it does not).
* A rich text is measured in one font weight but bold and italic spans are drawn in another face, so lines with marks run past the edge or overlap. Workaround: marks are drawn as a flow of single-style runs.
* `RichText` links always call `open_url`; there is no handler for an internal link. Workaround: own click handler per run.
* Emoji without a font are drawn blank but take their width; the bundled subset (`blinc_noto_emoji::register()`) lacks many (box glyphs).
* `text(..).italic()` shows upright text; a rich text with an italic span does draw italic (used for emphasis). The `code` flag of a span draws no monospace or chip (`flow.rs` does it itself).
* Layout of a document of 3000 paragraphs without `min_h(0)` overruns a wgpu buffer and aborts; a plain paragraph of 30 KB takes seconds in Blinc's text measuring (reproduction in the report).
* `BlincContextState::init` panics when called twice, also across threads (two pictures at once): `snapshot` serialises itself.
* `Scroll` has no `flex_1`; a `min_w` next to `w(0.0)` is ignored. The text area wraps at a narrower width than its box.
* `blinc_cn::cn_styles` documents `register_cn_styles(ctx)`, which does not exist in 0.6.0 (the bundle `cn_bundle()` does it).

Blinc notes for `avatar-group` (0.6.0):

* `cn::avatar` shows either the picture or the initials: a picture that cannot be loaded leaves a grey disc and never falls back to the initials. Workaround: a local path that is not a file is not passed on (addresses cannot be checked without loading).
* A picture appears only after a few frames (it fades in); an offscreen test must draw several frames with a pause. Reproduction: draw one frame of `cn::avatar().src(<png>)` and the disc is white.
* Emoji without a font in the initials draw blank (same as the text notes above).

Notes on keys (Blinc 0.6.0): **Enter and Space never arrive as key events** when an element has the keyboard: the window gives Tab, Enter and Space to its navigation first (`handle_navigation_key`), which clicks the focused element (a `POINTER_DOWN`/`POINTER_UP` on that node, no key event after it). `bind_keys` therefore also listens for that click, only while that element is the keyboard target (a mouse press clears the keyboard mode, so a mouse click is not taken for Space), and reports it as `Key::Activate`; Enter and Space cannot be told apart. All other keys are broadcast to every key handler. The test helper `Input::key` follows the window's order (navigation first, then the router's focused dispatch, then the broadcast). Earlier: a window may deliver a key press to every key handler (broadcast), which is how the reader's Ctrl+S could act twice. Our `bind_keys` compares the handler's node with `keyboard_focused_node()` (falls back to the element's own focus flag when Blinc has none) and ignores keys while a text input has focus. Tested in process with two lists in one tree.

Test isolation: Blinc keeps "a text input has the keyboard" process-wide, and a widget ignores keys while it is set; a test that typed into a filter field made the next key test fail now and then. `serial()` (the lock every Blinc test holds, because theme and reactive state are process-wide singletons) now also clears that focus; `text_focus_does_not_leak_into_the_next_test` pins it.

Tests of this crate's own widgets give the same verdict with and without system fonts (checked in a private mount namespace with `/usr/share/fonts` emptied; script `nofonts.sh` is not committed): they assert structure (element ids and sizes), and add pixel checks of text only when `has_fonts()` says text draws.

Text wraps instead of being cut in every widget (rows of the sortable list, names in the share dialog, captions, reasons). Blinc measures wrapped text slowly: a few hundred characters of long unbroken text in a dozen rows make a debug-build test take many seconds (tests keep such strings short). Chosen rows of the share dialog and failed transfers are announced when they are out of sight.

Blinc notes for the chat components (0.6.0):

* **A `blinc_core::reactive::effect` that writes a signal (here: asks a `Stateful` to draw again) hangs the program** (deadlock on the graph lock; found by a test that never ended). Reproduction: an effect that reads a signal and calls `State::update` on another state in its body. Workaround: the write is done from a short thread (`MessageList::on_scroll`).
* A `blinc_cn` button label with a space in it at the small size drew as "Tryagain" once ("Try again"); not understood, the default label is now "Retry".
* Scroll content height is `f32`: a conversation of 100 000 messages is about 9.6 million pixels, below the 16.7 million where one pixel can no longer be told apart. Beyond that, positions get coarse (not handled).
* `ElementHandle::on_ready` is the only way found to learn an element's laid-out size from our code (`Div` has no layout callback; only `Stateful` has `on_layout`, and nested stateful elements have the key problem noted above).

Blinc notes for `tasks` (0.6.0): a text area under the pointer takes the wheel for itself, also with nothing to scroll, so a page stops scrolling while the pointer is over one (seen through `dispatch_scroll_chain`, `tests/tasks_small.rs`). Blinc notes for `lightbox` (0.6.0): the image element loads the whole file at its full size (no downscaling on load) and shows nothing, not an error, for a file it cannot decode; only a missing local file is caught by us. An image fades in over its first frames; the first frame is empty. A `Button` has `id` only after `build_component()`.

Limits:

* `DocumentSource` is synchronous; a slow source blocks the interface thread.
* The tree is built completely (all nodes) once, because the Blinc tree is not lazy.
* Table columns share the width by the length of their longest text (no automatic table layout in Blinc).
* The reader's redraw counters are signals (`use_signal_keyed`), not `State`: `State::update` does not reach the live areas when a picture was drawn earlier in the same process (test `tests/refresh.rs` fails with `State`). A host must keep one `ReaderWidget` (see its `build` docs).
* The tree is rebuilt with every sidebar redraw and Blinc keys tree state by call site and counter, so folders that were opened by hand may close again; a blocked `open` can leave the tree highlight on the clicked row. Not fixed; needs a stable tree instance from Blinc.
* Keys are tested through a built widget (`tests/keys.rs`, `broadcast_key_event`): Ctrl+S, Alt+Left, Esc does nothing, `keys(false)`.
* Table column alignment is not applied; a table whose columns do not fit starts each column at its longest word (at most 160 px) and shrinks them to the room there is, so words wrap inside their columns, also in the middle of a long word, and no column is cut off (Blinc has no minimum content width and no sideways scroll for a table inside a page); the editor text area is not monospace.

## Chat components (provisional, Thread 1, item 5)

Source: `docs/en/programs/apps/assistant/index.md` (patterns from the Strata, CodeAF and Zed analyses), ADR 0053 and 0054, the messenger contract draft 0.2 (read only, to make the shapes fit). **Components know nothing of the messenger, a model or any API**: neutral data types, content through traits, no network code, no streaming transport (the host feeds the components).

| Component | State |
|---|---|
| `tool-call` (widget `tool_call`) | done: `ToolCall` (id, name, kind, state, summary, risk, end, detail, result, options, revision), `ToolCalls` (kept by id: an update replaces where it stood, never appends; a lower revision is `Stale`; a settled call is final), `ToolCallView` handle (clonable, no guard returned), `Labels` from the caller. **Second review round (2026-11-06). What changed, what is still open.**

## Charts (`crates/fs-components-charts`) - provisional

Source of the requirements: `docs/en/components/charts.md` (Vega-Lite subset, own Rust interpreter, mandatory text alternative, scene description so charts can be plugins). The Vega-Lite specification (v5/v6 schema and docs) is the standard that is read; no code of Vega, Vega-Lite, Blinc or any chart library is used.

**Why a new crate.** `widgets` stays the home of text and tree. A chart is a widget (it knows its data model when built: a spec with inline rows, ADR 0005, CONVENTIONS section 2), but it brings its own pure layers (spec, data, scales, layout, colour) with a lot of tests and one dependency (`serde_json`) that the other widgets do not need. A separate crate keeps those layers testable without Blinc being involved and lets other threads work in `widgets` without touching charts.

**Layers (each one testable alone, the first four without Blinc):**

| Layer | Pattern | What |
|---|---|---|
| `spec` | none (pure functions, `parse` is the entry point over small readers); `check.rs` is a Specification (pure rules), `channel.rs` and `mark.rs` are pure reader functions (none) | JSON to a typed `Spec`. Every property that is not read is a named refusal (`Obj::finish`); nothing is ignored |
| `data` | none (pure functions: read, aggregate, prepare); `cell.rs` and `time.rs` are Value objects (`Cell`, `Parsed`); `aggregate.rs` and `jsnum.rs` are pure functions (none) | rows to `Datum`s; reads numbers, categories, ISO 8601 times; aggregates; drops or breaks and *counts* what cannot be drawn (`Report`) |
| `scale` | Value objects (`Linear`, `Band`); pure functions for ticks and formats (none); `mod.rs` only re-exports (none) | linear (halved terms: no overflow), band/point, calendar ticks on the wall clock of the data, number and time formats with the caller's marks |
| `layout` | none (pure functions: `build` keeps the order, the mark is chosen by `match`, there is no trait; `describe.rs` and `notes.rs` are pure too); `Axis` is a Value object | `Spec` + data + `Labels` + `Measure` to a `Scene` (plain shapes with colour *roles*); a fixed-point loop settles the margins |
| `color` | none (pure functions: greedy farthest point, colour maths, colour-vision matrices) | series colours from the theme accents, judged by simulated colour vision |
| `view` | Adapter (+ Visitor in `draw.rs`) | `ChartView::build(w, h)` returns `impl Element`: a Blinc canvas, plus text elements for rotated labels |
| `alt` | none (pure functions; `Table` and `TextAlternative` are plain data) | text alternative: summary and the drawn data as a table |

**Accepted subset (provisional; everything else is refused with a message that names it).**
Marks `bar`, `line`, `area`, `point`, `arc` (string or object; object properties `type`, `innerRadius` on arc, `point` on line/area, `interpolate: "linear"`). Channels `x`, `y`, `color` (nominal only), `theta` (arc). Field types `quantitative`, `nominal`, `ordinal`, `temporal`. Per channel: `field` (nested `a.b`, escaped `a\.b`), `type`, `aggregate` (`count`, `sum`, `mean`/`average`, `min`, `max`), `title`, `axis` (`null`, or `title`, `grid`, `labels`), `scale` (`zero`, `nice`, `domain: [min, max]` of a quantitative field, `type: "linear"`), `sort` (`ascending`, `descending`, `null`, an explicit list, the other axis as `x`, `y`, `-x`, `-y`), `stack` (`zero`/`true`, `normalize`, `null`/`false`), `legend` (`null`). Top level: `$schema` (v5 or v6), `title` (string or `{text}`), `description` (becomes the summary of the text alternative), `width`, `height` (numbers), `data.values` (array of objects), `mark`, `encoding`, `usermeta`, `name`. Defaults follow Vega-Lite: zero and nice for quantitative x/y (no zero on the x of a line or area; with a `domain`, zero and nice only when asked for, and then applied to it), band padding 0.1/0.05 for bars, point padding 0.5, ascending category order, ticks `ceil(length / 40)`, label angle -90 on discrete x, stacks ordered by the natural order of the colour values, never by `color.sort` (vertical bar and area: first on top; horizontal bar and pie: first at the zero end or at 12 o'clock), `normalize` on absolute values, `sort: "-y"` by the channel's own aggregate, else the sum on a stacked axis and the smallest value otherwise, a count is quantitative whatever `type` says, numbers read as JavaScript reads them (`true` 1, `[5]` 5, `"0x10"` 16, `""` 0), 0.7 opacity for unaggregated points only (bars and areas are opaque, as in Vega-Lite), `invalid` mode `break-paths-show-path-domains` (paths break at an invalid value, other marks leave the row out).
Refused by name, among others: `transform`, `layer`, `facet`/`repeat`/`concat`, `params`, `config`, `bin`, `timeUnit`, `condition`, `format`, other channels (`size`, `shape`, `opacity`, `tooltip`, `text`, `detail`, `order`, `x2`/`y2`, `xOffset`, ...), other marks (`rect`, `rule`, `text`, `tick`, `circle`, `square`, `trail`, `boxplot`, `errorbar`, `geoshape`), `url`/`name`/`format` data, `color` that is not nominal, bars over time or over two number axes, bars without a zero baseline, a line with a non-quantitative y, `stack: "center"`, other aggregates, bracket field paths, scale types other than linear, mark properties not listed (`tooltip`, `color`, ...).
**Verified against real Vega-Lite.** `tests/golden/` holds 51 small cases (spec, mark geometry as fractions of the plot, colour order, axis labels) made with Vega-Lite 6.5.0 run headless in node (scripts in `tests/golden/tools`, nothing is installed system-wide, `cargo test` needs no node). 40 are geometry and order and 11 are tick labels (10 compared; `l10` shows labels Vega-Lite hides). Vega-Lite 5.23.0 was not run for these goldens (only 6.5.0); the default plot size of v5 (200) is taken from its documentation.

**Departures (all deliberate or known; an accepted spec must otherwise mean what Vega-Lite says).**
* *Time zones (provisional, the owner is asked).* Vega-Lite reads a date-only text (`2024-03-10`) as UTC, a date-time without offset as the viewer's local time, and draws the axis in the viewer's local time (`scale.type: "utc"` switches to UTC). We use no machine zone at all: a text without offset is wall-clock and is never converted; a text with an offset sits on the UTC line and the axis is written in the offset of the first value. So a chart looks the same on every computer; it differs from Vega-Lite for dates without an offset when the viewer is not in UTC, and `timeUnit` and `nice` on a time scale (which round to local days) are refused. A field mixing times with and without an offset is refused. `scale.type: "utc"` could carry the same meaning later.
* A literal colour is refused (colours come from the theme); more colour categories than the theme offers are refused when drawn.
* A line of one point is drawn as a dot (Vega-Lite draws nothing).
* Series also differ by line pattern and symbol shape (colour-blind readers). Blinc 0.6 draws no dashes (`Stroke::dash` is read by nothing), so the layout cuts a dashed line into its dashes (`layout::dash`), tested with pixels in `tests/draw_dash.rs`. An earlier version of this file claimed dashes were drawn: they were not.
* Sectors are separated by a thin line in the surface colour.
* A negative value on an arc is left out and counted; Vega-Lite draws a sector with a negative extent that overlaps the others.
* A row without the field and a row with `null` are two categories (as in Vega-Lite, `null` first, then missing). Vega-Lite stacks the two onto one pile (a quirk); we draw two bars.
* More marks than `Metrics::max_marks` (10000): lines and areas are merged per pixel column, points of a series per half pixel; bars and sectors beyond the budget are all left out, with a note (a part of a bar chart on a full axis would mislead).
* A sort by `x`/`y` on the colour channel is refused; `stack` is accepted only on the value axis of a bar or area (and `null` on a line or point); a time scale cannot be `nice`; sizes above 1000000 pixels are refused.
* Tick labels use the Unicode minus (as Vega-Lite) and all digits below 1e21, then the form `1e+21`.


**Data problems (what happens, all tested):** empty data: "No data" in the chart and an empty table; one point: line drawn as a dot, bar as one bar, point as one point, domain of equal values widened (zero included, or +-half the value); all values equal: same; `null`/absent/`"NaN"`/`""`/`"Infinity"`/array/object/boolean in a number field: the row is left out of bars, points and arcs and breaks lines and areas, and a note under the chart and the text alternative count it by field and reason (`Report`); numeric text such as `"12.5"` counts as a number (as JavaScript reads it); `null` in a category field is the category "null" (caller's word); negative bars hang below zero; negative angles are left out and counted; huge values (1.7e308): scales halve their terms, sums that overflow are `Overflow` issues, means are summed per term; 100000 rows: prepared in about 0.3 s and laid out in 0.2 s (debug build); Blinc's drawing surface holds 20000 primitives by default and silently drops the rest, so marks are drawn after axes, title and legend, lines and areas are merged per pixel column (first, lowest, highest, last point: the same picture), points of one series on the same half pixel are one point, and anything beyond `Metrics::max_marks` (10000) is counted in a note (`Labels::note_omitted`); a merged area is drawn as one-pixel strips because filling a polygon of that many points took minutes in Blinc; long labels: cut with an ellipsis at 180 px (axes, legend) and at the chart width (title, notes); labels that would overlap are thinned by parity; unicode: text is passed through as it is; dates: ISO 8601 only, an impossible date (`2023-02-29`, hour 24) is invalid; the zone is the data's own: a text without offset is wall clock and never converted, a text with an offset is placed on the UTC line and the axis is written in the offset of the first value; a field that mixes the two is refused (`prepare` error) because the chart would have to guess a zone; across a daylight-saving change noon-to-noon is 23 hours apart on the axis when the data says `+01:00` then `+02:00`.

**Colour.** Series colours are chosen from the theme (`Primary`, `Warning`, `Info`, `Secondary`, `Accent`, `Success`, `Error` and lighter or darker copies) by greedy farthest-point selection, judged as seen with normal vision, protanopia, deuteranopia and tritanopia (Machado et al. 2009 matrices, CIE 1976 Delta E). A colour needs contrast 3:1 against the surface (WCAG 1.4.11) and two series colours need a worst-case difference of 15. The default light and dark themes give five. `Look::rgb` gives the colours as plain numbers; no Blinc type is public. A chart with more series than the theme offers shows a notice instead of repeating colours (`ChartView::build`); more than 8 is refused when the chart is read. `charts.md` says nothing on colour; the rule above is our choice (provisional, the numbers 3, 15 and 8 are open).

**Text alternative.** `Chart::text_alternative(labels, max_rows)` and `ChartView::text_alternative()`: summary (the spec's `description`, else made from the data) and a table of what is drawn, plus the notes about what is not. Blinc has no ARIA or accessibility tree, so the view cannot expose it to a screen reader yet; the program has to show it (a "show data" view) or hand it over itself. Listed as a Blinc gap.

**Words.** Every sentence, number mark, month name and time pattern comes from `Labels` (caller), English by `Default`. The chart's own words are the spec's (title, axis titles, field names).

**Tooltips, keys, focus: not built.** Blinc could do hover (`on_mouse_move` on the element), but a tooltip needs redraw state and a decision on where it floats; nothing is shown on hover. The pure part exists: `Scene::hit_at(x, y, slack)` returns the datum under a point as text (`field: value` per line), so a program can show it its own way. The chart has no keys and takes no focus, so it cannot clash with keys of other widgets; a keyboard way through the data (arrows step through the hits, each read as text) is planned and will be optional per widget (`.keys(bool)`, no shared state, no lock guard in any API).

**Blinc notes (0.6.0):** the GPU primitive buffer (`max_primitives`, default 20000) truncates without error: draw 30000 `fill_circle` in a canvas and everything past the 20000th, including later axes, vanishes (only a `tracing` warning); `fill_path` of a self-overlapping polygon of 200000 points does not finish in minutes; `canvas` draws text unrotated: the transform moves the origin of a text but not its glyphs (reproduce: `push_transform(rotate)` then `draw_text`); rotated labels are therefore text elements rotated by the layout engine. A canvas asks for a frame every vsync unless `redraw_while` says no (done). Blinc has no text alternative or ARIA for any element.
